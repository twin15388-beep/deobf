# Продолжение: Luarmor/Jnkie и проверка ошибок — 22 октября 2026

**Нового допустимого игрового Lua пока нет:** в [`dobf scripts 1.0/`](../dobf%20scripts%201.0/) осталось **61 файл — 26 восстановлений/частичных результатов и 35 прежних `(src)`**. Здесь не добавлялись `(src)`, загрузчики, сырой байткод или скрипты из коллекции без установленного разрешения на перепубликацию. Ниже — воспроизводимая **статическая распаковка внешней оболочки**, исправления ошибочной классификации и точная граница между ней и восстановлением игры. Pastefy и API **для получения скриптов** не использовались; ключи не подбирались, HTTP-поставку не запрашивали, Lua/Roblox не запускали.

## Исправлена ложная метка `loader_only`

В [отчёте от 21 октября](api-delivery-2026-10-21.md) файл из уже существующего архива `Deobfuscator-Luraph-V15-master.zip/sample/BloxFruit.lua` ошибочно назван **только Luarmor-загрузчиком**. Это **ранее вложенный в чужой инструмент** результат по Luraph v15 (191 163 байта, SHA-256 `4863cc8547cddd373e90656367305fb0b5587bc476f01482ce7e015e01012063`); он совпадает побайтно с `sample/output/Blox Fruit.lua`. Защищённый вход — другой файл, `sample/Blox Fruit.lua` (646 487 байт, SHA-256 `6dd9eb35957f644934b3e7759dcc7b1c32ffb499a47f21504a0001dfc2d037f7`). **Мы не повторяли** его восстановление и не деобфусцировали удалённые Luarmor-ссылки.

В локальном результате действительно есть код для **Blox Fruits**, а не один UI: запрос `CommF_:InvokeServer("GetFruits")` (получение списка фруктов, без дополнительных аргументов); `RegisterAttack:FireServer(0)` и `RegisterHit:FireServer(v19, hits, nil, str2)` (боевые вызовы; смысл временных переменных `v19`/`str2` не доказан); `FishingRequest:InvokeServer("StartCasting")` и `("CastLineAtLocation", vector2, 100, true)` (рыбалка, координата `vector2`, остальные аргументы сохранены как в образце); `CommF_:InvokeServer("SetTeam", "Pirates"/"Marines")` (выбор команды). Есть вызовы внешних Luarmor-загрузчиков и сторонней UI-библиотеки, поэтому **это не полное автономное восстановление**. В уже готовом файле есть **строковые упоминания** `LPH_ENCSTR`/`LPH_ENCFUNC`, которые сами по себе не превращают его в ещё одну VM. Права на размещение именно игрового примера третьей стороны отдельно не подтверждены; в каталог его не переносили. Синтаксис/поведение в Roblox и полнота не проверены.

Исправленный [`inspect_api_delivery.py`](../scripts/inspect_api_delivery.py) для `--loader` возвращает **`loader_with_inline_code`** вместо `loader_only`, если видит вызовы `FireServer`/`InvokeServer` вне комментариев и строк, но **не** объявляет их игровыми функциями доказанно (`gameplay_verified=false`). Также он выделяет `loader_with_protected_code` для файлов с SDK и распознанной VM. Эти метки — *подсказки для изучения целого файла*, а не доказательство, что функция относится к игре, указанной на кнопке хаба. Комментарий с `:FireServer` или строковый литерал `"LPH_ENCSTR"` больше не подменяют распознавание. Исправлен разбор локального JSON `{"encoding":"base64","data":"..."}`; при двух разных телах в полях JSON теперь `ambiguous_json_fields`, а не произвольный выбор первого/«более защищённого». `--out` внутри репозитория разрешён только в игнорируемом `local-results/`. Дополнительно Jnkie `/public/.../download`, `/delivery/...` и CDN `.lua` теперь имеют обезличенные типы маршрутов, **без идентификатора или подписи ссылки**.

## Реальный локальный образец с Jnkie SDK и встроенным Luraph

Из [vyxonq-dev/obfuscator-samples@82e582f](https://github.com/vyxonq-dev/obfuscator-samples/tree/82e582fcdd78948212192e1ceb748769ef3e8494) *точечно через `git clone --filter=blob:none --sparse`* исследован `VM Compressed/Unknown/6bb278cf01086730.lua`: **326 779 байт**, SHA-256 `cb220be3b5f1e3c2688fd49289eca5707e402471ab4634aec7a1fc6124c5d3cd`. В начале файла — ~3 191 байт открытой обвязки WindUI/Jnkie SDK (`/sdk/library.lua`); затем заголовок **Luraph v14.6** и два длинных Lua-литерала `LPH`. Это **не доказательство**, что VM-тело было получено от Jnkie по SDK: файл лишь содержит оба участка. В открытом префиксе нет вызовов игрового `FireServer`/`InvokeServer` или подтверждённого плейса; совпадения `GPO` глубоко в бинарно-похожей строке нельзя считать названием игры.

Новый **собственный ограниченный офлайн-инспектор** [`scripts/inspect_luraph_envelope.py`](../scripts/inspect_luraph_envelope.py) независимо повторяет только проверенный для этого формата шаг: два `LPH` base85 (слова big-endian) → raw LZMA1 с явными ограничениями на вход/выход, проверкой двух литералов, конца LZMA-потока и паддинга. Он не запускает даже встроенный SDK и никогда не отправляет запросов. Результат на точном локальном входе:


Вывод второго инструмента: `envelope_unwrapped=true`, **`vm_decompiled=false`, `game_source_recovered=false`, `gameplay_verified=false`**. Названия двух экспортируемых файлов явно маркируют интерпретатор и VM-байткод; содержимое не коммитили. Для игрового результата понадобятся законный защищённый вход конкретной игры, корректный разбор **именно v14.6** опкодов/констант, восстановление игровых обработчиков и проверка поведения. Для Jnkie как отдельной серверной защиты авторизованного тела нет, поэтому её **не объявляем взломанной**.

## Luarmor и пять приоритетных игр

В том же незалицензированном репозитории два локальных файла с шапкой Luarmor (`Unknown/2b9864a4992c87f5.lua`, 1 991 байт; `Unknown/6e2d667f3bb0c404.lua`, 1 661 байт) остались **загрузчиками**; серверного тела там нет. `VM Compressed/Unknown/59158c6331ae0883.lua` (245 374 байта) — многоигровой хаб: текстовые вкладки **Trident Survival** и **Grand Piece Online** ведут к Luarmor/иным `HttpGet`-загрузкам. Найденные в *целом* файле несколько `FireServer`/`InvokeServer` нельзя приписать этим двум вкладкам без трассы; `loader_with_inline_code` — только файловая подсказка. Другой найденный по сочетанию `GPO`/`jnkie` файл `Prometheus/Unknown/Unknown/93bcf6ccd7abe248.lua` имеет совпадения внутри случайно выглядящей закодированной таблицы, **не подтверждённый Jnkie-код GPO**. У коллекции не обнаружена LICENSE; код из неё **не публикуем**.

По Lone Survival, Slayers 2 и King Legacy нового допустимого серверного тела/пары «защищённый вход → проверенный игровой Lua» также нет. Проверенные ранее варианты и уже имеющийся ограниченный King Legacy core — [в предыдущем отчёте](api-delivery-2026-10-21.md). Новые `(src)` пользователь попросил не добавлять. Ни размер хаба, ни слова в имени скрипта или в зашифрованной строке не заменяют конкретные игровые обработчики.

## Почему найденные «инструменты Jnkie/Luarmor» не дают исходник сами по себе

- [`Aditya-lua/luadevirt`](https://github.com/Aditya-lua/luadevirt) фигурировал в поисковой выдаче, но **GitHub API вернул 404** для самого репозитория 22 октября; воспроизвести инструмент невозможно, поэтому его обещания не засчитываются.
- [`Mazsigiit/Jnkie-Script-Dumper`](https://github.com/Mazsigiit/Jnkie-Script-Dumper) (MIT) прямо предупреждает в README: **нужен уже действительный ключ**, скачиваемое тело остаётся обфусцированным. [`alvin12127/jnkie_retrieve`](https://github.com/alvin12127/jnkie_retrieve) и [`qopxxcrobloxscript-cyber/Jnkie-deobf`](https://github.com/qopxxcrobloxscript-cyber/Jnkie-deobf) содержат HTTP GET/POST к доставке/службе. Исходники просмотрены локально после `git clone`, **не запускались**, API не вызывали.
- [`PumbaaDev/luau-decompiler`](https://github.com/PumbaaDev/luau-decompiler) (MIT, `ee07098c`) — офлайн-инструмент для **нативного Luau bytecode**, а здесь стадия 2 — **пользовательский Luraph VM-формат**, не подменяемый Luau. В этой среде нет `cargo`/собранного бинарника; неприменимый декомпилятор не выдаём за испытанный на Jnkie VM.

**Контроль:** 68 Python-тестов (включая 18 тестов доставки и три новых теста оболочки), проверка **61** опубликованного игрового файла, **40** архивов исходников, один Node-тест и `git diff --check` проходят. Синтетические тесты проверяют отсутствие исполнения, ограничение размеров, фильтрацию комментариев/секретов и отказ записывать сырые стадии в отслеживаемые папки. Внешняя VM не исполнялась, Roblox не проверялся.
